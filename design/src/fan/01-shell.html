Sidebar & mobile tab bar

Four destinations, mapping one-for-one onto the acceptance criteria: Home is the roll-up and the empty state, Tickets is scenario 2, Travel is scenario 3, and Settings keeps the account reachable without a second login (scenario 5). Both shells come from one definition in design/partials.mjs, so the sidebar and the tab bar can never disagree about what exists or what order it sits in.

1
The fan's own name and email sit at the top, above the nav. This is their account, not a console — the admin sidebar puts the user last for exactly the opposite reason.
2
Active is a solid lime pill, not the admin's subtle wash. On a phone in daylight the wash is invisible. Fill, weight and colour all change together, so the state survives greyscale and forced-colors.
3
42px nav rows, 62px tab targets — up from the admin's 32px. Thumbs, not a mouse.
4
Tickets carries a dot, never a count. We cannot know how many tickets a fan has until the ticket endpoint exists, and a made-up number is worse than admitting something is unfinished. It disappears the day the endpoint lands.
5
Same four, same order, both shells. The tab bar is the sidebar with the labels shrunk — nothing is re-ordered or hidden on collapse, so muscle memory survives the breakpoint.

Why no rail. The admin sidebar collapses to a 72px icon rail because staff live in it all day and want the screen back. A fan visits for a minute at a time and reads labels, so the fan shell has two states — full sidebar, or bottom tabs — and no third one to learn.

Scenario 5 is a navigation guarantee, not a visual one: every one of these moves is a client-side route change against a session cookie already in hand, so nothing here can prompt for a second login.
